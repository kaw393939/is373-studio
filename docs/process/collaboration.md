# Work together and review a real task

**Bring the current version and one task. Take turns trying each other's work, then make a useful improvement.** A plan can be reviewed before the app exists.

## Use this five-step review

1. **State the goal.** “Try submitting a request without a service,” or “Tell me how you would check this story.”
2. **Let the peer try without coaching.** Observe their actions and questions. If you must help, record what help was needed.
3. **Give specific feedback.** Name a useful strength, the main observed obstacle and its effect. Suggest one manageable next action.
4. **Record and respond.** Use an issue in the project's repository. The owner chooses a response, links the change or explains another decision.
5. **Retest.** Repeat the task on the changed version, record the result, then close a resolved issue. Keep an unresolved one open with a next step.

**Swap roles.** In a trio, rotate owner, reviewer and observer so everyone tries another's work. A sincere strength helps someone see what to keep; do not bury an important failure in a required praise sandwich.

> **Fictional teaching example:** “The source links were clear. Importing twice created duplicate notices, so I could not tell what was new. Keep each source item only once.” The owner fixes duplicate handling, links the change, and the peer repeats the import. This example is not actual human review evidence.

## Share the whole process

Split small, meaningful slices with comparable effort. Each person makes design decisions, implements work and checks another person's work. Integrate early and adjust the remaining work when effort changes. Commit or issue counts do not prove equal contribution.

Keep observations, decisions and links in the existing project record; no new review essay is needed. Reuse a continuing issue when appropriate, while meeting any posted lesson-specific issue/PR requirements. For the planned final-project process, each project needs real peer feedback, a meaningful change and a retest. AI approval, a fake customer and a simulated partner cannot replace people.

## Why this feedback style?

Toastmasters emphasizes the goal, observed behavior, personal reactions and useful encouragement. We adapt that approach to software tasks. The spec, issue, PR and retest are course additions, not a Toastmasters program or endorsement.
