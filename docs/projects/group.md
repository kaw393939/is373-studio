# Deliverable 3 - Group content system + problem research

**Your product is one shared hosted content system. Your research is the reader, course problem, sources and workflow.** Choose one existing IS373 problem and build with a partner. The Canvas syllabus offers information isolation caused by social media, automatic educational-content publishing, or another content ETL pipeline. Start with the reader and content process, research the problem, and justify vector retrieval, graph retrieval or both.

This is separate from each person's **Deliverable 1, portfolio**, and **Deliverable 2, RAG app**. Each portfolio later explains its owner's contribution to this shared system. Keep evidence under **3. Group content system + problem research** in the team record.

## Choose a bounded problem

| Course direction | A manageable first workflow | Evidence of a useful result |
| --- | --- | --- |
| Information isolation | Import a small permitted source collection on one topic; help a reader discover and compare related material | Visible source coverage, traceable comparisons, relevant retrieval and honestly stated gaps |
| Educational-content publishing | Import approved material; create a source-supported briefing, study guide or question set; review and publish | Accurate source references, review state and a usable published result |
| Another content ETL task | Identify a reader and a content problem; agree an extract/transform/load process with the instructor | Validated inputs, meaningful transformation and useful reviewable output |

The first option does not require proving that you solved polarization. The second can automate preparation while retaining human approval before publication. Use permitted public sources or labeled synthetic fixtures and keep a source manifest.

## Research the system and process

Describe the reader, problem, source permission, import, cleaning/deduplication, data representation, retrieval, optional generation, review and delivery. Write three to five observable user stories and a small evaluation set. Compare two approaches and select one with a reason. All members research vector, graph and RAG concepts; the group's implementation choice follows its actual questions and constraints.

Build one complete useful path and a meaningful alternative experiment or presentation. The group system must add a shared workflow beyond copying the individual chat: for example, source collection plus comparison, a review/publication queue, or a reusable content transformation with quality checks.

## Share design, development and checking

Begin with a partner and discuss any team-size adjustment with the instructor. Both partners should make design decisions, implement meaningful work and check the other person's changes. Give each task an owner and a different reviewer, integrate early and keep actual contribution links.

| Example slice | Owner | Reviewer |
| --- | --- | --- |
| Source contract, import, validation and repeat-import checks | Partner A | Partner B |
| Retrieval/output flow, review/publication and task checks | Partner B | Partner A |
| Architecture choice, integration, evaluation and demo | Both, with named work | Cross-review and another real peer |

This is an example split. Adjust for comparable effort; commit counts alone do not establish contribution. A simulated customer can support discovery but cannot replace a teammate or human peer review.

## Delivery and review

Provide a usable hosted demo, repository, reproducible setup, source trace and actual checks. Keep the database/private services protected and label limits. Each person submits the shared record link plus their own contribution note in the group review box. Use one shared record throughout Plan, Build, Release and Improve.
