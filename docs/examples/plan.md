# A small Plan example for all three deliverables

**Fictional teaching example.** This shows the size and organization of a Plan, not a completed project, real student reflection or evidence that any checks passed. Use your own employer research, permitted sources and decisions. Read original postings and record their current status before relying on them.

## 1. Individual portfolio + career research

**Reader and direction:** an internship reviewer interested in AI application development. The student compares customer-facing delivery with product engineering and provisionally chooses application/product work. Senior postings describe a longer-term direction, not present eligibility.

**Research record:** three original employer sources, exact titles, date checked, level/eligibility, three responsibilities per posting, required/preferred skills, existing evidence, one gap and next action. These original pages are examples of where to begin; this example does not substitute for the student's three completed records:

- [OpenAI FDE](https://openai.com/careers/forward-deployed-engineer-(fde)-sf-san-francisco/): investigate customer discovery, integrations and delivery; verify level/travel constraints.
- [Citi Senior AI Engineer](https://jobs.citi.com/job/jersey-city/senior-ai-engineer-banking-technology/287/102155117424): investigate AI application work and engineering requirements; label the senior level.
- [Anthropic Product Engineer, Computer Use](https://job-boards.greenhouse.io/anthropic/jobs/5238637008): investigate full-stack product work and model/application integration; verify eligibility.

**Evidence map:** user problem → reader/task statement; retrieval skills → RAG case study with source/query trace; delivery/teamwork → own group contribution and actual review/check links.

**Portfolio outline:** introduction and target direction; individual app case study and demo; group case study with named contribution; repository/contact links. Compare an evidence-first homepage with a biography-first layout using the same content; provisionally choose evidence-first so a reviewer can find the work quickly. These are proposed design choices, not measured user findings.

**Gap/next action:** learn to evaluate retrieval; prepare five expected-evidence questions by the Nov 12 workshop. Do not claim that the planned app is already a skill demonstrated.

## 2. Individual RAG app + technical research

**Reader/task:** new members of a fictional club need answers grounded in its short policies. Use five synthetic documents authored for the exercise: membership, events, code of conduct, committee responsibilities and contacts. Give them stable source IDs and versions; no private student information.

**Comparison:** keyword search offers a simple baseline; vector retrieval may help paraphrased questions; graph retrieval may help ownership/relationship questions. Choose a vector-first experiment for passage-oriented questions, while documenting what graph modeling would add. This is a hypothesis to test, not a benchmark claim. A student with different questions can justify graph or both.

**Planned flow:** permitted source → clean text → heading/paragraph chunks with source IDs → embeddings → persistent index → question retrieval → model context → answer with usable references. Compare heading-based boundaries with a fixed-length split; keep the unit explicit and record lost context. Database, embedding/generation models, access and resource limits must be confirmed before implementation.

**Five evaluation questions:** who may join; a paraphrase of the conduct/support rule; which committee owns events; where to request help; and the date of the next meeting, intentionally absent from the corpus. Record expected source IDs before running queries. Require an honest insufficient-evidence response for the last question.

**Observable stories/checks:** a reader can open an answer's source; repeating import creates no duplicate records; absent evidence is acknowledged; a visitor cannot use administration/import controls. At Plan these are intended checks, with no invented pass results.

## 3. Group content system + problem research

**Course problem:** educational-content publishing. **Reader:** a learner who needs a short reviewed briefing with links to its source material. **Scope:** one source collection, one briefing type and one editor review/publish flow.

**Two approaches:** publish raw source links, or transform sources into a draft briefing that a person checks before publishing. Choose the second only if the team can preserve references and show a useful transformation. Begin with labeled synthetic fixtures or material whose reuse is permitted. A workflow beyond an individual chat is required.

**Stories/checks:** import retains source IDs; repeating the import does not duplicate drafts; drafts remain private; an editor can approve a checked item; visitors can read only published items and open source references. Record these as planned until actually executed.

**Owner/reviewer:** A owns source/import validation and B reviews; B owns review/publish behavior and A reviews; both integrate and explain their named contributions. A real peer later tries the workflow. No invented teammate work or peer feedback.
